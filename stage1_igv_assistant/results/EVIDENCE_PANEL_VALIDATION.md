# evidence_panel Validation

**Tool:** `evidence_panel` (added 2026-08-11, commits `deb67c9`/`dec56c5`) — generates one screenshot per evidence layer instead of a single combined image, each with the IGV settings that isolate that layer visually.

This session had no working example output for `evidence_panel` since it was added the same day. The first two runs below cover both ends of the signal spectrum: a positive control (synthetic translocation, signal present on all 4 layers) and a negative control (real HCC1143 locus, no real signal on any layer) — confirming the tool's window selection, layer skipping, and dominant-clip-side detection all work correctly whether or not there's anything to find. A third run (§3, added 2026-08-11 in a later session) adds the one case neither control covers: a real, confirmed-ground-truth variant — completing the set.

## Note on this session's environment

The first `evidence_panel` attempt failed for an infrastructure reason unrelated to the tool itself: the MCP server process (launched via `~/.claude.json`, pointed directly at the `rda` conda env's Python) had no `PATH` entry for that env's `java` binary, so IGV's batch script exited immediately with `java: not found`. Fixed by adding `PATH` (rda `bin/` first) to that server's `env` in `~/.claude.json` and reconnecting the MCP session. Not a bug in `bam_tools.py`/`server.py` — see `stage1_igv_assistant/README.md`'s Known limitations for the general note; worth knowing if `evidence_panel`/`igv_screenshot` fail silently again in a fresh MCP session.

## 3. Confirmed-variant case — real GIAB HG002 deletion (chr1:115,686,862)

**BAM:** `https://ftp-trace.ncbi.nlm.nih.gov/ReferenceSamples/giab/data/AshkenazimTrio/HG002_NA24385_son/NIST_HiSeq_HG002_Homogeneity-10953946/NHGRI_Illumina300X_AJtrio_novoalign_bams/HG002.GRCh38.300x.bam` (real, remote, streamed over HTTPS — not a local/cached copy).
**Locus:** chr1:115,686,862 — the real GIAB HG002 deletion breakpoint used throughout `REAL_DATA_VALIDATION.md` and `LLM_SESSION_3_BLIND.md`'s post-fix re-verification, and the only locus in this repo with independently confirmed ground truth (a real GIAB-called deletion, not a synthetic fixture or an unconfirmed real-data locus). `gene_at_locus` was attempted 3x in this session to attribute the disrupted gene and got `HTTP 500` all three times — Ensembl was intermittently unavailable for most of this session (the same flakiness hit `TEST 7`/`TEST 18` of the automated suite earlier today, both of which passed on retry). Not re-asserting the gene name here from outside this session's tool calls; `test_bam_tools.py` TEST 7's own Ensembl-sourced result earlier today did resolve it, for anyone cross-referencing.

Illumina 300x paired-end short-read data, novoalign-aligned. `applicable_layers` returns 3 of 4 (`discordant_pairs`, `soft_clipped_reads`, `read_depth`); `split_reads` is correctly excluded — 0 SA tags in 1000 sampled reads, consistent with novoalign not emitting chimeric alignments (same reason `split_reads` is excluded for the 2018-era HCC1143 BAM in §2, different underlying cause — aligner choice here, not alignment era). `bam_stats_at_locus` (chr1:115,686,612–115,687,112): 1,017 reads, mean depth 230.48, mean MAPQ 70, 0% low-MAPQ — a clean, non-repetitive locus.

### Depth panel: pre-fix vs. post-fix

This is the first `evidence_panel` (and first dedicated, coverage-only `read_depth` layer) generated at this locus since the 2026-08-11 depth-computation fix (`git log` — "Fix read-count-vs-depth bug, global-min depth ratio, and fraction-based soft-clip scoring"). The only prior screenshots of this region are `session2_chr1_deletion.png`/`_v2.png`/`_v3.png` (2026-08-10, documented in `LLM_SESSION_2_WITH_VISUAL.md` §10), which predate both the fix and the `evidence_panel` tool itself — they're single manual `igv_screenshot` calls with full alignment rows visible (not the coverage-only panel style `evidence_panel` produces), over a different, larger window (chr1:115,685,862–115,691,222 vs. today's chr1:115,683,862–115,689,862), so this is not a pixel-identical before/after comparison. Two things *are* directly comparable:

- **The scale ceiling dropped, because the true numbers dropped.** `session2`'s fixed coverage scale (0–550) was derived from the pre-fix `read_depth_profile`'s reported `max_depth` of 518 — a number `LLM_SESSION_2_WITH_VISUAL.md`'s own correction note (written after the fix) flags as inflated by the read-counting bug, estimating true per-base depth over a comparable span at roughly 100–320. Today's standalone `read_depth_profile` call measured `max_depth` 319.13 for this exact locus, and `evidence_panel` auto-computed its scale as 0–367 (319.13 × 1.15 headroom) — landing almost exactly inside that predicted corrected range, not the old 0–550.
- **The dip's existence and rough location did not change.** `LLM_SESSION_2_WITH_VISUAL.md`'s correction note already established that "the described shape — depth dropping in the window starting exactly at the breakpoint... — held up under re-measurement with the corrected tool; the absolute depth numbers did not." Today's panel confirms the same: a real, visually clear depth reduction centered on the breakpoint, using the corrected computation throughout.

Net effect of the fix on this panel, specifically: the *rendering* changed (lower, correct scale ceiling; today's panel is also a different, purpose-built coverage-only view rather than a full-alignment screenshot with a manually-tuned track height), but the underlying *finding* — a real depth drop at this breakpoint — was never a false artifact of the bug and remains visually and numerically supported.

## Bottom line

`evidence_panel` now has example output covering all three cases that matter for validating it: a synthetic positive control (signal on all 4 layers, ground truth from the fixture's own construction), a real negative control (no real signal on any layer, ground truth from `RESULTS_HCC1143.md`), and a real positive control (§3, ground truth from GIAB's confirmed call) — and in all three, the per-layer screenshots are visually consistent with the evidence already established elsewhere. The positive control additionally confirms the one thing only this tool's split-read layer can show: individual SA-tag partner-locus labels rendered directly in the image, each independently pointing to a partner position tightly clustered around chr8:47,000,000. The negative control shows the tool correctly reporting *why* a locus is weak (scattered discordant partners, scattered clip positions, flat depth) rather than just asserting it, and correctly skipping a structurally-inapplicable layer. The real confirmed-variant case (§3) shows genuine signal rendering correctly post-fix, including one honest caveat worth remembering when reading any `discordant_pairs` panel: `UNEXPECTED_PAIR` coloring conflates inter-chromosomal discordance with anomalous insert-size pairs, so a visually busy discordant_pairs panel doesn't necessarily mean the `discordant_pairs` *count* found anything — check both. Together, all three validate the tool's plumbing (per-layer window selection, layer skipping, dominant-clip-side detection, SA-tag grouping, auto-scaling) on signal-present, signal-absent, and real-confirmed-variant data.
