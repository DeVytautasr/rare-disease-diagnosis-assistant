## SECTION 3 — Error handling audit

Directly probed each tool against the real HCC1143 validation BAM
(`stage1_igv_assistant/data/bam/HCC1143.normal.21.19M-20M.bam`) and a
nonexistent/non-BAM path. Full script output below is summarized in the
table; raw output is in the audit session.

| Bad input | Result |
|---|---|
| Nonexistent BAM path | **Clean error dict** for all of `get_bam_stats_at_locus`, `count_discordant_pairs`, `count_soft_clipped_reads`, `get_split_reads`, `get_read_depth_profile`, `summarize_breakpoint_evidence`. **`check_reciprocal_breakpoint` does NOT return an error** — see Finding C2 below, this is the most serious individual finding in this section. |
| BAM path exists but is not a BAM (`.md` file used as stand-in for `.txt`) | Clean error dict (`"file does not contain alignment data"`) for the tools tested. |
| Chromosome not in header (`chrZZ`) | **Unhandled `ValueError: invalid contig`` — crashes**, not caught, for `get_bam_stats_at_locus`, `count_discordant_pairs`, `count_soft_clipped_reads`, `get_split_reads`, `get_read_depth_profile`, `summarize_breakpoint_evidence`, `check_reciprocal_breakpoint` (7 of 9 tools). `get_gene_at_locus` handles it cleanly (HTTP 400 → error dict). See Finding C1. |
| Position beyond end of chromosome | **Unhandled `ValueError: start out of range`** — same root cause as above (reproduced on `get_bam_stats_at_locus`, `count_discordant_pairs`). |
| Negative position | `get_bam_stats_at_locus` (which takes raw `start`/`end` with no clamping) **crashes** with `ValueError: start out of range (-100)`. Window-based tools (`count_discordant_pairs`, etc.) clamp internally via `max(0, position - window_bp)` and so degrade gracefully to an empty-window result instead of crashing — inconsistent handling across tools, but not itself a crash. |
| `start > end` | **Unhandled `ValueError: invalid coordinates: start > stop`** in `get_bam_stats_at_locus` and `get_read_depth_profile` (both take raw `start`/`end` from the caller with no validation). |
| Empty `bam_paths` list for `run_igv_screenshot` | Does not crash; returns a clean-looking error dict, but only after running IGV with zero `load` lines and going through the full launch/poll path rather than validating up front — slow failure, not a fast/clear one. |

**Root cause for the crash family (C1):** every affected function wraps only
the `pysam.AlignmentFile(bam_path, "rb")` open call in `try/except`. The
subsequent `bam.fetch(chromosome, start, end)` call — where all of these
`ValueError`s actually originate — is unprotected in every tool.

**Finding C1 — CRITICAL, reproduced with a realistic real-world trigger:**
The real validation BAM (`HCC1143.normal.21.19M-20M.bam`) uses GRCh37-style
bare contig names (`'1'`, `'21'`, `'X'`, ...), **not** `chr`-prefixed names.
Every tool's docstring (`bam_tools.py` and `server.py`) documents the
`chromosome` argument as `"e.g. 'chr1' or '1'"`, actively inviting the
`chr`-prefixed form. Calling any of the 7 affected tools with `"chr21"`
against this exact BAM — a completely natural mistake for an LLM agent that
has no visibility into the BAM's actual contig naming convention — throws an
unhandled `ValueError` that propagates out of the tool entirely, rather than
the structured error dict the project's own anti-hallucination design
requires every tool to return.

**Finding C2 — CRITICAL:** `check_reciprocal_breakpoint` calls
`count_discordant_pairs` twice and reads `primary.get("discordant_pairs", 0)`
/ `reciprocal.get("mate_chromosomes", {})` etc. without ever checking for an
`"error"` key in either sub-result. If either underlying call fails (bad BAM
path, crash on the chromosome name per C1, etc.), the function **silently
treats the failure as "zero discordant pairs found"** and returns a normal,
well-formed verdict — e.g. `"INSUFFICIENT EVIDENCE at both positions"` — with
no error field at all. This is not just a missing error path; it actively
manufactures a negative clinical finding out of a tool failure, which is
exactly the failure mode the project's "anti-hallucination" design (server.py
instructions: *"Do not invent signal"*) exists to prevent, except the
invention is happening in the tool layer rather than the LLM layer.

## SECTION 4 — Consistency audit

- **`server.py` tool count:** `grep -c "^@mcp.tool()" server.py` → **9**.
  Matches the README's "9 tools" claim and matches the 9 functions imported
  from `bam_tools.py`.
- **README.md tool list:** All 9 names (`bam_stats_at_locus`,
  `discordant_pairs`, `soft_clipped_reads`, `split_reads`,
  `read_depth_profile`, `breakpoint_evidence_summary`, `gene_at_locus`,
  `reciprocal_breakpoint`, `igv_screenshot`) match the `@mcp.tool()`-decorated
  function names in `server.py` exactly. **No drift here.**
- **Default parameter drift — CRITICAL (Finding C5):**
  `server.py`'s `split_reads` wrapper declares
  `window_bp: int = 300, min_mapq: int = 20`, while the underlying
  `bam_tools.get_split_reads` declares `window_bp: int = 200, min_mapq: int = 0`.
  An LLM calling the MCP tool `split_reads` with no explicit arguments
  silently gets a **wider window and a mapq filter that doesn't exist in the
  underlying function's own defaults**. All other wrappers checked
  (`discordant_pairs`, `soft_clipped_reads`, `read_depth_profile`,
  `reciprocal_breakpoint`) have matching defaults between the two layers.
- **`breakpoint_evidence_summary` wrapper hides tunable parameters (Finding
  I9):** `bam_tools.summarize_breakpoint_evidence` accepts `window_bp` and
  `min_mapq`; the `server.py` wrapper's signature only exposes `bam_path`,
  `chromosome`, `position`, `label` — `window_bp`/`min_mapq` are silently
  hardcoded to the function's defaults with no way for the LLM to override
  them, and this limitation isn't mentioned in the wrapper's docstring.
- **Docstring/return-field drift (Finding I8):** `get_gene_at_locus` returns
  `clinical_note`, `gene_count`, `gene_start`, `gene_end` in each gene entry,
  none of which are mentioned in the `server.py` `gene_at_locus` docstring's
  "Returns" description (it only mentions gene name, biotype, strand,
  intergenic flag).
- **Stale threshold reference across two tools (see also Section 5, Finding
  C4):** `server.py`'s own docstring for `read_depth_profile` states
  `"depth_ratio_min_to_mean < 0.6 suggests deletion"` (matches
  `get_read_depth_profile`'s code) while its docstring for
  `breakpoint_evidence_summary` doesn't mention a threshold at all (the 0.7
  value lives only in `bam_tools.py`'s docstring/comments) — two different
  numeric thresholds for conceptually the same "is this a deletion" judgment
  are live in the same file, undocumented as being different from each
  other anywhere a reader would see them side by side.

## SECTION 5 — Scientific correctness review

**Finding C4 — CRITICAL, verified in code (not just docs):**
`get_read_depth_profile` (tool 5) computes
`"likely_deletion": depth_ratio_min_to_mean < 0.6` — this line has **not**
been updated since the depth threshold was recalibrated. Separately,
`summarize_breakpoint_evidence`'s composite scoring uses
`depth_ratio < 0.7 → 15 pts`, `< 0.3 → 25 pts` (commit `d5fef9f`, "Calibrate
depth window: ±2kb, threshold 0.7"). **These are two different, live
thresholds for the same underlying judgment, in the same file, and
`summarize_breakpoint_evidence`'s own returned dict embeds both**
(`depth_profile.summary.likely_deletion` computed at 0.6, alongside
`depth_score` computed at 0.7). A locus with `depth_ratio` between 0.6 and
0.7 — plausible territory, per `GIAB_PUBLIC_DATA_VALIDATION.md`'s own numbers
(0.618–0.707 observed on real GIAB data before the ±2kb window fix) — gets
`likely_deletion: False` from the raw tool output sitting right next to a
`depth_score: 15` (i.e., "this is evidence of a deletion") from the composite
in the exact same response. An LLM reading both fields in the same dict has
no way to know which one is "current."

**Threshold provenance, by layer:**
- **Discordant-pair, soft-clip, split-read tiers** (0 / 7.5 / 15 / 25 at
  fraction cutoffs 0 / 0.1–0.2 / 0.1–0.3 / ≥0.2–0.3 depending on layer): no
  calibration citation anywhere in code or docs. These appear to be
  arbitrary round-number choices, not empirically derived — there is no
  equivalent of `GIAB_PUBLIC_DATA_VALIDATION.md` for these three layers the way
  there is for the depth threshold.
- **Depth threshold (0.7, ±2kb/200bp window):** the only layer with a
  documented calibration source — one confirmed locus (GIAB HG002 deletion,
  chr1:115,686,862), replicated across two sequencing technologies (PacBio
  HiFi and Illumina 300x), explicitly flagged in the code comment itself as
  "a starting point, not a validated general threshold" (single locus, not
  two independent loci). This honesty in the comment is good practice, but
  doesn't change that it's one data point.

**Equal weighting across structurally inapplicable layers:** The composite
always sums 4 independent 0–25 components to a 0–100 `evidence_score`,
regardless of whether a layer can possibly fire for the technology in
question. `case_object.py`'s `SequencingInfo.applicable_evidence_layers`
property exists specifically to express "which layers are informative for
this technology" — but **it is never called from `bam_tools.py`**; grep
confirms its only two references are its own definition and one assertion in
`test_bam_tools.py` TEST 9. The scoring function has no knowledge of it. The
project's own real-data validation confirms the practical consequence: on
PacBio HiFi (unpaired), discordant-pairs is always 0/25 regardless of true
evidence; on Illumina/Novoalign (no SA tags), split-reads is always 0/25
regardless of true evidence. Both real validated datasets topped out at
"3/4 signal_layers" for structural reasons that have nothing to do with
variant quality — meaning **"strong" (≥70) is mathematically unreachable on
either of the two real datasets this tool has actually been validated
against**, since the best either could do is 3 layers × ≤25 = 75, but only if
the 3 applicable layers all hit their top tier simultaneously; in practice
the real HG002 run reached "moderate," not "strong." Excluding inapplicable
layers from the denominator (e.g., scoring out of 3×25=75 rather than 100
when only 3 layers apply) would make `evidence_strength` comparable across
technologies. As implemented, it is not — a "moderate" on Illumina 300x
and a "moderate" on PacBio HiFi are not necessarily comparable evidence
strength, since each is being measured against a 100-point scale that
includes a layer neither technology could ever contribute to.

**"Weak/moderate/strong" labelling meaningfulness:** Given the above, the
label is only meaningful in an absolute sense (higher score = more raw
evidence collected) but is misleading as an implied confidence tier, since
its ceiling silently depends on sequencing technology rather than on
evidence quality. This is a real, current design gap — not something the
docs claim is already solved (the docstring in `bam_tools.py` is accurate
about what the code does; the gap is that the code doesn't implement what
`case_object.py`'s own schema was seemingly designed to enable).

## SUMMARY

### CRITICAL — will cause wrong results or crashes

1. **7 of 9 tools crash with an unhandled `ValueError`** (not a structured
   error dict) on an out-of-header chromosome name, a position beyond the
   chromosome end, or `start > end` — because only the BAM *open* call is
   wrapped in `try/except`, not the `.fetch()` call. Reproduced with the
   realistic case of passing `"chr21"` against the real validation BAM,
   whose contigs are named `"21"` — exactly the naming ambiguity the tools'
   own docstrings invite ("e.g. `'chr1'` or `'1'`"). Affects
   `get_bam_stats_at_locus`, `count_discordant_pairs`,
   `count_soft_clipped_reads`, `get_split_reads`, `get_read_depth_profile`,
   `summarize_breakpoint_evidence`, `check_reciprocal_breakpoint`.
2. **`check_reciprocal_breakpoint` silently converts a tool failure into a
   fabricated negative finding.** It never checks the `"error"` key on its
   two internal `count_discordant_pairs` calls, so a bad BAM path (or any
   crash from Finding 1) produces a normal-looking
   `"INSUFFICIENT EVIDENCE"` verdict instead of an error — directly
   contradicting the project's anti-hallucination design goal.
3. **`run_igv_screenshot`'s documented default (`color_by="MATE_CHROMOSOME"`)
   is not a valid option in the installed IGV 2.17.4 build** and crashes
   IGV's batch executor (`IllegalArgumentException: No enum constant...
   ColorOption.MATE_CHROMOSOME`), which then hangs in the AWT thread until
   the tool's poll loop times out — every default-settings call to this
   tool silently fails after burning the full timeout. Verified valid
   values in the installed build: `INSERT_SIZE`, `READ_STRAND`,
   `PAIR_ORIENTATION`, `UNEXPECTED_PAIR` (the likely intended replacement
   for translocation coloring), and others — `MATE_CHROMOSOME` is not among
   them. All documented successful screenshots in this repo used
   `INSERT_SIZE`; `MATE_CHROMOSOME` — the explicitly recommended value for
   translocations in both docstrings — has apparently never worked
   end-to-end. TEST 10 does not catch this because it only asserts on
   `batch_script` string contents, never on `success`.
4. **Two different, live depth-ratio thresholds for the same "likely
   deletion" judgment coexist in the same file and in the same returned
   dict:** `get_read_depth_profile`'s own `likely_deletion` field still uses
   `< 0.6` (never updated), while `summarize_breakpoint_evidence`'s
   `depth_score` uses the later-calibrated `< 0.7`. A locus with a ratio
   between 0.6 and 0.7 gets contradictory signals from two fields in one
   response.
5. **`server.py`'s `split_reads` MCP wrapper has different default
   parameter values than the underlying `bam_tools.get_split_reads`**
   (`window_bp` 300 vs 200, `min_mapq` 20 vs 0) — an LLM calling the tool
   with no explicit arguments gets silently different filtering than the
   function's own documented defaults.

### IMPORTANT — misleading docs, missing tests, or design concerns

6. `get_read_depth_profile` has **zero direct test coverage** — not even
   imported in the test file; only exercised indirectly and unasserted as a
   sub-call. Corresponds to the unexplained TEST 4/TEST 5 numbering gap.
7. No test exists for the MCP server itself starting up or exposing exactly
   9 tools.
8. `summarize_breakpoint_evidence` never asserts that its 4 component
   scores sum to `evidence_score` — the exact invariant that broke in
   production once already (commit `c093ed4`) and was only caught by an
   LLM session, not by this test suite; there is still no regression test
   for it.
9. TEST 10's real-IGV branch asserts only on `batch_script` string content,
   never on `success` — it currently reports `PASSED ✓` even though the
   real screenshot generation fails 100% of the time in this environment
   (see Critical Finding 3).
10. `case_object.py`'s `SequencingInfo.applicable_evidence_layers` — designed
    to say which of the 4 evidence layers are technology-applicable — is
    never consulted by `summarize_breakpoint_evidence`'s scoring logic.
    Component scores are always summed over a fixed 0–100 scale even when 1
    or 2 of the 4 layers are structurally inapplicable to the sequencing
    technology, meaning `evidence_strength` labels aren't comparable across
    technologies. Confirmed in practice: both real validated datasets
